\section{Systemsicherheit}
\subsection{Malware (\blue{MAL}ixious Soft\blue{WARE})}
\fatsf{Definition:} Schädlicher Code des Angreifers, der auf der Maschine des Opfers ausgeführt wird\\
\fatsf{Ziel:} Vielseitige Angriffe möglich, u.a.
\begin{itemize}
    \item Löschen von Dateien
    \item Senden von Spam Nachrichten von Opfermaschine
    \item Denial of Service Angriff als Teil eines Botnets
    \item Harddisk Verschlüsselung zur Erpressung von Lösegeld
    \item Private Informationen extrahieren (Passwörter etc.)
    \item Physikalische Zerstörung des Computers
\end{itemize}

\subsubsection*{Spezialfälle}
\begin{itemize}
    \item \blue{Ransomware:} Trojaner, der Dateien verschlüsselt und nur gegen \enquote{Lösegeld}-Zahlung wieder freigibt (oder auch nicht)
    \item \blue{Scareware:} Trojaner, der z.B. als Virenscanner vermeintlich gefundene Viren gegen Bezahlung löschen soll
\end{itemize}
\begin{defBox}
    \fatsf{Zero-Day-Exploits:} Malware nutzt häufig neue Schwachstellen, bei der Entwickler keine Zeit hat (zero days), um Security Patch bereitzustellen
\end{defBox}

\subsubsection*{Würmer}
\begin{itemize}
    \item Programme, die sich automatisch \red{über das Netz selbst verbreiten}
    \begin{itemize}
        \item \fatsf{Mit oder sogar ganz ohne Nutzerinteraktion}, daher auch die Klassifikation \enquote{wormable} für Schwachstellen, die komplett automatische Verbreitung erlauben
    \end{itemize}
    \item \blue{Beispiel:} Sasser (2004)
    \begin{itemize}
        \item Nutzte eine Schwachstelle (Buffer Overflow) im Windows 2000/XP Dienst LSASS aus, um sich selbst auf Zielsystem zu kopieren
        \begin{itemize}
            \item Patch zur Schließung der Schwachstelle war schon veröffentlicht, aber nicht überall installiert
        \end{itemize}
        \item Auf dem Zielsystem angekommen scannt der IP Bereiche nach neuen verwundbaren Zielen
        \item Schadfunktion: Herunterfahren des Computers in unregelmäßigen Abständen
    \end{itemize}
\end{itemize}
\subsubsection*{Viren}
\begin{itemize}
    \item Programme, die ihre \red{eigenen Code in \enquote{Wirtsprogramme}} einfügen und sich bei Nutzerinteraktion verbreiten
    \item Bekannte Virentypen:
    \begin{itemize}
        \item Executable infectors
        \item Polymorphic viruses
        \item Metamorphic viruses
        \item ...
    \end{itemize}
\end{itemize}
\subsubsection*{Viren: Executable Infectors}
\begin{itemize}
    \item Virus infiziert ein ausführbares Programm
    \item Virencode wird im Wirtsprogramm eingefügt und Kontrollfluss entsprechend adaptiert
    \item Aktion des Virus (\enquote{payload}) kann von externen Faktoren abhängig sein (z.B. Zeit, Netzwerkadresse, ...)
    \begin{infoBox}
        Ein \fatsf{Payload} ist die eigentliche \fatsf{Schadfunktion} eines Virus, Wurms oder einer anderen Malware.\\
        \fatsf{Vergleich:} Der Virus ist das \enquote{Transportmittel}, der Payload ist die \enquote{gefährliche Fracht}
    \end{infoBox}
    \begin{figure}[h]
        \centering
        \includegraphics[width=1\textwidth]{Thema_8_Images/Viren: Executable Infectors.jpeg}
    \end{figure}
    \item Erkennung einfach anhand des Virus Codes $\rightarrow$ statische Virussignatur
\end{itemize}
\subsubsection*{Statische Virussignatur}
\begin{itemize}
    \item Berechnung eines Algorithmus oder Hashes, um Virus eindeutig zu identifizieren
    \item Format: <Virus CRC16/CRC32/Hash Value> | <Virus Name>
    \begin{itemize}
        \item 0095C3A4|STONED.LESZOP.A
        \item 0086C7BE|STONED.MARCH6.A
    \end{itemize}
\end{itemize}
\subsubsection*{Viren: Polymorphe Viren}
\begin{itemize}
    \item Virus ist (bis auf kurze Entschlüsselungsroutine) \red{verschlüsselt}
    \begin{figure}[h]
        \centering
        \includegraphics[width=0.8\textwidth]{Thema_8_Images/Viren: Polymorphe Viren.jpeg}
    \end{figure}
    \item Code für die Entschlüsselung besagt: \enquote{Entschlüssele verschlüsselten Viruscode mit Schlüssel und führe den Virus Code aus}
\end{itemize}
\begin{itemize}
    \item Virus verändert Erscheinungsbild mit jeder Replikation
    \begin{figure}[h]
        \centering
        \includegraphics[width=0.8\textwidth]{Thema_8_Images/Viren: Polymorphe Viren 2.jpeg}
    \end{figure}
    \item Beide Viren nutzen \fatsf{unterschiedliche} Schlüssel $\rightarrow$ Alles bis auf den kurzen Code für die Entschlüsselung sieht \enquote{zufällig} aus
    \item \red{Erkennung deutlich schwieriger} (großer Teil ist zufälliger String) $\rightarrow$ Erkennung fokussiert auf Entschlüsselungsroutine
\end{itemize}
\subsubsection*{Viren: Metamorphe Viren}
Jedes mal wenn sich der Virus repliziert, erzeugt er eine semantisch unterschiedliche Version des Virus Codes\\
$\rightarrow$ Gleiche High-level Aktionen aber mit kleinen unbedeutenden Abweichungen\\
$\rightarrow$ Beispiele für äquivalenten Code
\begin{itemize}
    \item add 0 to register
    \item subtract 0 from register
    \item xor 0 with register
    \item no-op
    \item Veränderung von conditional statements (if/else)
    \item Ersetzen eines Algorithmus durch anderen (z.B. mergesort durch quicksort)
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{Thema_8_Images/Viren: Metamorphe Viren.jpeg}
\end{figure}
\begin{itemize}
    \item \red{Rwriter Code} besagt: \enquote{Erzeuge semantisch unterschiedlichen Code des Virus Codes}
    \item \red{Achtung:} Rewriter Code kann selbst modifiziert werden
\end{itemize}
\subsubsection*{Metamorphe Viren: Gegenmaßnahmen}
Erkennung anhand des Verhaltens:
\begin{itemize}
    \item Anstelle des Syntax muss das Verhalten des Virus analysiert werden
    \item Untersuchung der Aktionen, die der Virus ausführt
    \item Antiviren Firmen suchen nach Verhaltensmustern, um eine Virussignatur zu erstellen
\end{itemize}
Strategien eines Virus, um Erkennung zu verhindern:
\begin{itemize}
    \item Bösartiger Viruscode wird erst nach langer Wartezeit ausgeführt
    \item Erkenne Codeanalyse und stoppe die Ausführung des Virus Codes
\end{itemize}
$\rightarrow$ Katz- und Mausspiel zwischen Viren- und Antivirenentwicklern
\subsubsection*{Trojaner}
\begin{itemize}
    \item Programm, das neben bekannter Funktion \red{auch \enquote{unerwünschte} Nebeneffekte} hat
    \item Beispiel: Sunburst (2020)
    \begin{itemize}
        \item Kontroller über Systeme von Behörden weltweit (Dateien ableiten, Systemdienste deaktivieren)
        \item Aktiv seit März, gefunden im Dezember
        \item Einfallstor: Updateroutine der Software Orion (IT Administrationssoftware)
    \end{itemize}
    \item Thompson's Compiler (1984) - eher theoretisch interessant
    \begin{itemize}
        \item Modifiziere C Compiler so, dass bei Übersetzung von Tools wie Login-Modul bekannte Passwörter akzeptiert werden
        \item Sobald Compiler eine neue Version seines eigenen Codes übersetzt, wird der gleiche Schadcode eingefügt\\
        $\rightarrow$ Schwierig zu finden, da modifizierter Quellcode gelöscht und nur der modifizierter Compiler bereitgestellt wird
    \end{itemize}
\end{itemize}
\subsubsection*{Ransomware}
\begin{itemize}
    \item Bezeichnet eine \red{Schadfunktion}, keinen Verbreitungsweg
    \begin{itemize}
        \item Bsp. Wannacry: Ransomware und gleichzeitig Wurm
    \end{itemize}
    \item \red{Verschlüsselt nahezu alle Dateien auf den PC} (keine Systemdateien)
    \item z.B. hybride Verschlüsselung:
    \begin{itemize}
        \item jede Datei wird mit einem neuen symmetrischen Schlüssel verschlüsselt
        \item dieser wird mit dem public key des Angreifers verschlüsselt und an die Datei angehängt
    \end{itemize}
    \item Fordern Lösegeld (\enquote{ransom}) für Zugriff auf den privaten Schlüssel (häufig in Kryptowährungen)
    \item Meist ein Schlüsselpaar pro Opfer auf dem Server gespeichert
\end{itemize}

\subsection{Ausführung von C Programmen}
\subsubsection*{Call: Compiler, Assembler, Linker, Loader}
\fatsf{4 Schritte zur Ausführung eines C-Programms:}
\begin{itemize}
    \item \fatsf{Compiler:} Konvertiert C-Code in Assembler-Code (RISC-V, x86)
    \item \fatsf{Assembler:} Konvertiert Assembler-Code in Maschinencode (raw bits)
    \item \fatsf{Linker:} Löst Abhängigkeiten von externen Bibliotheken auf (brauchen wir hier nicht)
    \item \fatsf{Loader:} Einrichtung von Speicherplatz und Ausführung des Maschinencodes
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{Thema_8_Images/Call.jpeg}
\end{figure}
\subsubsection*{Memory Layout}
\fatsf{Loader} weist das Betriebssystem an, dem Programm einen großen Speicherbereich zur Ausfürhung zuzuweisen
\begin{itemize}
    \item Jedes \fatsf{Byte} des Speichers hat eine eindeutige \fatsf{Adresse}
    \item Bei einem \fatsf{32-Bit-System} hat der Speicher \fatsf{32-Bit-Adressen}
    \item Jede \fatsf{Adresse} bezieht sich auf ein \fatsf{Byte}, d.h. wir haben $2^{32}$ Bytes Speicherplatz (32-Bit-System)
\end{itemize}
Häufige Darstellung des Speichers als \fatsf{Tabelle:}
\begin{itemize}
    \item In jeder \fatsf{Zelle} steht ein \fatsf{Byte}
    \item Die Zellen einer Zeile können zusammengefasst werden zu einem \fatsf{Wort (4 Bytes = 1 Wort)}
\end{itemize}

\subsection{X86 Architektur}
\subsubsection*{X86 Memory Layout}
\fatsf{Speichernutzung bei Ausführung eines Programms}
\begin{itemize}
    \item \fatsf{Code:}
    \begin{itemize}
        \item Der Programmcode selbst (acuh \enquote{Text} genannt) in Maschinencode
    \end{itemize}
    \item \fatsf{Daten:}
    \begin{itemize}
        \item Statische Variablen/Konstanten, die beim Start des Programms zugewiesen werden
    \end{itemize}
    \item \fatsf{Heap:}
    \begin{itemize}
        \item Dynamisch zugewiesener Speicher mit \fatsf{malloc} und \fatsf{free} 
    \end{itemize}
    \item \fatsf{Stack:}
    \begin{itemize}
        \item Lokale Variablen und Stack Frames
        \item Bei tieferen Funktionsaufrufen, wächst er nach unten
    \end{itemize}
\end{itemize}
\subsubsection*{Stack Frame}
\begin{itemize}
    \item Wenn der Code eine Funktion aufruft, wird auf dem Stack Platz für lokale Variablen geschaffen
    \begin{itemize}
        \item Dieser Platz wird als \fatsf{Stack Frame} für die Funktion bezeichnet
        \item Der Stack Frame verschwindet, sobald die Funktion zurückkehrt
    \end{itemize}
    \item Der Stack startet an höherer Adresse
    \item Jedes Mal, wenn Code eine Funktion aufruft, \fatsf{wächst der Stack nach unten} und schafft zusätzlichen Platz
    \begin{itemize}
        \item Hinweis: Daten auf dem Stack, z.B. eine Zeichenkette (String), werden nach wie vor von der niedrigsten Adresse bis zur höchsten Adresse gespeichert
        \item Das \enquote{Herunterwachsen} geschieht nur, wenn zusätzlicher Speicher zugewiesen werden muss
    \end{itemize}
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=0.3\textwidth]{Thema_8_Images/Stack Frame.jpeg}
\end{figure}
\subsubsection*{Register}
Spezielle \fatsf{Speicherbereiche} auf der \fatsf{CPU}, die jeweils \fatsf{4 Bytes} speichern können
\begin{itemize}
    \item \fatsf{Adressierung} unterscheidet sich zu Memory Layout
    \begin{itemize}
        \item \fatsf{Speicher:} Adressen als 32-Bit-Zahlen
        \item \red{Register werden mit Namen bezeichnet} (EBP, ESP, EIP, ...), nicht mit Adressen
    \end{itemize}
    \item Um Überblick über aktuellen Stack-Frame zu behalten, speichern wir zwei Zeiger in Register:
    \begin{itemize}
        \item \fatsf{EBP}-Register (\enquote{Basiszeiger}) zeigt auf den Anfang des aktuellen Stack Frames
        \item \fatsf{ESP}-Register (\enquote{Stackzeiger}) zeigt auf das untere Ende des aktuellen Stack-Frame
        \item \fatsf{EIP}-Register (\enquote{Befehlszeiger}) speichert die Adresse des gerade ausgeführten Maschinenbefehls im Code Segment
    \end{itemize}
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=0.3\textwidth]{Thema_8_Images/Register.jpeg}
\end{figure}

\begin{itemize}

    \begin{itemize}
        \item Dekrementiere den ESP, um mehr Speicher auf dem Stack zuzuweisen
        \item Speichern des neuen Wertes auf dem niedrigsten Wert des Stacks
    \end{itemize}
\end{itemize}

\subsubsection*{Funktionsaufruf in X86}
\begin{itemize}
    \item Beim Aufruf einer Funktion müssen ESP und EBP verschoben werden, um einen neuen Stack Frame zu erstellen
    \item EIP wird in den Code der aufgerufenen Funktion verschoben
    \item Bei der Rückkehr aus einer Funktion müssen ESP, EBP und EIP auf ihre alten Werte zurückkehren
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{Thema_8_Images/Funktionsaufruf in X86.jpeg}
\end{figure}
\subsubsection*{Wiederholung: Stack, Register}
\begin{itemize}
    \item Während Funktionsaufruf wird auf dem Stack Platz für lokale Variablen geschaffen (Stack Frame)
    \item Dieser Platz wird gelöscht, sobald die Funktion zurückkehrt
    \item Der Stack beginnt bei höheren Adressen und wächst nach unten
    \item Der Codeabschnitt enthält in Raw Bit, die Assembleranweisungen der Funktionen
    \item Wir speichern zwei Zeiger, die den Umfang des aktuellen Stack Frames definieren
    \item EBP wird für den oberen Teil des Stack Frames verwendet
    \item ESP für den unteren Teil des Stack Frames 
    \begin{itemize}
        \item Alles unter ESP ist undefiniert und wird ignoriert
        \item Beim Schreiben in Stack muss ESP angepasst werden, so dass er auf niedrigsten Wert referenziert
    \end{itemize}
    \item EIP zeigt auf den aktuellen Befehl in der Programmausführung
\end{itemize}
\subsubsection*{0. Initialer Stack}
\begin{itemize}
    \item Im Stack existiert ein Stack Frame für Funktion \fatsf{main}
    \item Jeder Stack Frame muss Platz für lokale Variablen haben und wächst nach unten (hier keine lokalen Variablen)
\end{itemize}
\fatsf{Merke:} Alle Werte der Register EBP, ESP und EIP müssen auf dem Stack abgelegt werden bei einem Funktionsaufruf, da diese sonst verloren gehen
\subsubsection*{1. Argumente der aufgerufenen Funktion}
\begin{itemize}
    \item Die Argumente werden dem Stack in umgekehrter Reihenfolge hinzugefügt
    \item ESP muss auf den untersten Wert des Stack Frames für die Funktion \fatsf{main} verweisen
\end{itemize}
\subsubsection*{2. Zwischenspeicherung EIP}
\begin{itemize}
    \item Als nächstes wird der aktuelle Wert von EIP auf den Stack gelegt
    \begin{itemize}
        \item Dies ermöglicht das Programm fortzusetzen nachdem die Funktion \fatsf{foo} zurückgekehrt ist
    \end{itemize}
    \item Wird manchmal auch als RIP (Return Instruction Pointer) bezeichnet
    \begin{itemize}
        \item Er zeigt, wohin wir im Programm in der Funktion \fatsf{main} als nächstes gehen müssen
    \end{itemize}
\end{itemize}
\subsubsection*{3. Zwischenspeicherung EBP}
\begin{itemize}
    \item Als nächstes wird der aktuelle Wert von EBP auf den Stack gelegt
    \begin{itemize}
        \item Dadurch können wir den obersten Punkt des vorherigen Stack Frames wiederherstellen, wenn wir zurückkehren
    \end{itemize}
\end{itemize}
\subsubsection*{4. Einstellen des Stack Frames}
\begin{itemize}
    \item Um den Stack Frame anzupassen, müssen wir alle drei Register aktualisieren
    \item Gefahrlos möglich da die alten Werte von EBP und EIP gespeichert wurden
    \item Altes ESP ist immer das untere Ende des Stacks, daher besteht keine Notwendigkeit, es zu speichern
\end{itemize}
\subsubsection*{5. Führe die Funktion aus}
\begin{itemize}
    \item Stack Frame bereit, die Anweisungen der Funktion zu verarbeiten
    \item Alle lokalen Variablen können auf Stack verschoben werden
    \item Durch aktuellen Wert von EBP können wir auch auf Variablen außerhalb des aktuellen Stack Frames zugreifen (z.B. Argumente)
\end{itemize}
\subsubsection*{6. Wiederherstellen}
\begin{itemize}
    \item Nach Beendigung der Funktion setzen wir alle drei Register wieder an ihren alten Wert zurück
    \item Verwende die in RIP und SFP gespeicherten Adressen, um EIP und EBP auf ihre alten Werte zurückzusetzen (durch Aufruf von pop)
    \item ESP wird auf das Ende des Stack Frames von \fatsf{main} zurückgesetzt 
    \begin{itemize}
        \item Beachte: Die Werte, die wir auf Stack geschoben haben sind immer noch da (wir überschreiben sie nicht, um Zeit zu sparen)
        \item Sie befinden sich unter ESP, so dass \fatsf{main} nicht mehr darauf zugreifen kann
    \end{itemize}
\end{itemize}

\begin{infoBox}[title=Was passiert bei Signed/Unsigned-Mischung?]
    Ein gefährliches Problem entsteht, wenn len ein \fatsf{signed int} ist, aber mit \fatsf{einem unsigned Wert} verglichen wird
    \begin{codeBlock}{}
        void func(int len) {
            if (len > (size_t)64)  // len wird zu unsigned gecastet!
                printf("len ist größer als 64\n");
        }
    \end{codeBlock}
    \begin{itemize}
        \item \fatsf{Gefahr:} Wenn len == -1, dann wird es zu 4294967295 auf 32-Bit-Systemen gecastet!
        \item \fatsf{Ergebnis:} -1 > 64 ist plötzlich WAHR!
    \end{itemize}
\end{infoBox}

    \centering
    \includegraphics[width=0.9\textwidth]{Thema_8_Images/signed-unsigned schwachstelle 2.jpeg}
\end{figure}
\subsubsection*{Integer Overflows verhindern}
Von allen Integers müssen die Bereiche überprüft werden
\begin{codeBlock}{}
    void safe (size_t len, char *data){
        if (len > SIZE_MAX - 2) //Überprüfe ob Überlauf möglich
            return;
        char *buf = malloc(len + 2);
        if (!buf)
            return;
        memcpy(buf, data, len);
        buf[len] = '\n';
        buf[len + 1] = '\0';
    }
\end{codeBlock}
Sehr aufwendig und fehleranfällig!
\subsection{Gegenmaßnahmen}
\subsubsection*{Memory Safe Programming Languages}
\begin{itemize}
    \item Hauptgrund für Buffer Overflows: C/C++ ist nicht Memory Safe
    \item Lösung: Benutze Programmiersprache mit \enquote{Memory Safety} (z.B. Java, Python, Go, Rust, ...)
    \begin{itemize}
        \item Überprüfe reservierte Speichergröße und verhindere undefinierten Zugriff auf Speicherbereiche
    \end{itemize}
    \item Warum werden nicht nur Programmiesprachen mit \enquote{Memory Safety} verwendet?
    \begin{itemize}
        \item Effizienz: in vielen Anwendungen nicht relevant
        \item Legacy Code
    \end{itemize}
\end{itemize}
\subsubsection*{Programmieren}
\begin{itemize}
    \item Defensives Programmieren: Füge Gültigkeitsprüfungen ein wo immer möglich 
    \begin{itemize}
        \item Beispiel: Überprüfe, ob ein Zeiger null ist bevor er dereferenziert wird
    \end{itemize}
    \item \enquote{Gefährliche} Operationen wie \fatsf{gets/strcpy/strcat/sprintf} vermeiden
    \begin{itemize}
        \item Varianten fgets/strncpy/strncat/snprintf benutzen
        \item Aber das ist gar nicht so einfach, z.B. \fatsf{gets(buf) $\rightarrow$ fgets(buf, size, src)}
        \item Wobei \fatsf{size} so gesetzt werden sollte, dass nicht über \fatsf{buf} hinaus geschrieben werden kann
    \end{itemize}
    \item Verwendung von Preconditions, Postconditions und Invarianten, die der Code erfüllen muss
    \begin{itemize}
        \item Sehr aufwendig $\rightarrow$ daher kaum verwendet in der Praxis
    \end{itemize}
    \item Testen
    \begin{itemize}
        \item z.B. Fuzzing: Teste Programmcode auf zufälligen Eingaben
        \item Problem: Code Coverage
    \end{itemize}
\end{itemize}
\subsubsection*{Ausnutzen eines Memory Safety Schwachstelle}
\begin{enumerate}
    \item Finde eine Memory Safety Schwachstelle (z.B. Buffer Overflow)
    \item Schreibe Shellcode des Angreifers an eine bekannte Adresse des Speichers
    \begin{itemize}
        \item Randomisierung der Adressen im Speicherbereich
    \end{itemize}
    \item Überschreibe den RIP mit der Adresse des Shellcodes
    \begin{itemize}
        \item Gegenmaßnahme: Stack canaries
    \end{itemize}
    \item Springe aus der angegriffenen Funktion zurück
    \item Führe Shellcode des Angreifers aus
    \begin{itemize}
        \item Markiere Speicherbereiche als nicht ausführbar
    \end{itemize}
\end{enumerate}
\subsubsection*{Gegenmaßnahmen: Stack Canary}
\fatsf{Idee:} Füge einen zufälligen Wert zum Stack hinzu und überprüfe, ob er verändert wurde
\begin{itemize}
    \item Beim Start des Programms erzeuge einen zufälligen geheimen Wert (\enquote{\blue{canary}}) und speichere ihn in einer globalen Variable
    \item Beim Beginn der Ausführung der Funktion speichere \blue{canary} direkt unterhalb SFP/RIP
    \item Beim Beenden der Funktion überprüfe, ob \blue{canary} gleich dem Wert der globalen Variable ist\\
    $\rightarrow$ Angreifer kann RIP nur überschreiben, wenn er \blue{canary} zerstört\\
    $\rightarrow$ Erkenne Buffer Overflow Angriff $\rightarrow$ Führe das Programm zum Absturz
\end{itemize}
\begin{figure}[h]
    \centering
    \includegraphics[width=0.3\textwidth]{Thema_8_Images/Stack Canary.jpeg}
\end{figure}
Stack Canaries werden vom Compiler eingefügt
\begin{itemize}
    \item z.B. in Visual C++ im Modus /GS (GuardStack)
    \item Fügt automatisiert ein paar Befehle zu anfälligen Code hinzu $\rightarrow$ meistens nur geringer Effizienzverlust
\end{itemize}
Stack Canaries umgehen:
\begin{itemize}
    \item Extrahiere den Wert des Stack Canaries: z.B. durch andere Schwachstelle im Programm
    \item Verhindere das Überschreiben des Stack Canaries: z.B. bestimmte Angriffe erlauben Überschreiben beliebiger Speicherpositionen
    \item Raten des Stack Canaries: z.B. relativ einfach auf 32-bit Systemen
\end{itemize}
\subsubsection*{Gegenmaßnahmen: Nicht ausführbare Speicherbereiche}
Speicherbereich muss häufig nicht gleichzeitig ausführbar und beschreibbar sein
\begin{itemize}
    \item Code: Ausführbar aber nicht beschreibbar
    \item Stack, Heap: Beschreibbar aber nicht ausführbar
    \item \fatsf{DEP:} Data Execution Prevention (alias $W_{rite} \oplus$ eXecute) in Windows
    \begin{itemize}
        \item Teile des Speichers werden als nicht ausführbar markiert\\
        $\rightarrow$ Shellcode kann nicht mehr ausgeführt werden
    \end{itemize}
\end{itemize}
\fatsf{Probleme:}
\begin{itemize}
    \item Im Code Speicherbereich befinden sich bereits zahlreiche ausführbare Befehle
    \begin{itemize}
        \item Beispiel: \fatsf{Return-Oriented Programming (ROP)}
    \end{itemize}
\end{itemize}
\subsubsection*{Return-Oriented Programming}
\begin{infoBox}
    \fatsf{Return-Oriented Programming (ROP)} ist eine Technik, bei der \fatsf{bereits bestehende, ausführbare Codefragmente} (sogenannte \enquote{Gadgets}) genutzt werden, um den Codefluss \fatsf{umzuprogrammieren}. Diese Technik wird oft in \fatsf{Systemen verwendet}, bei denen DEP aktiviert ist
\end{infoBox}
\begin{figure}[h]
    \centering
    \includegraphics[width=0.67\textwidth]{Thema_8_Images/Return-Oriented Programming.jpeg}
\end{figure}
\begin{infoBox}
    \begin{enumerate}
        \item \fatsf{Angreifer sucht nach kurzen, wiederverwendbaren Code-Schnipseln} (Gadgets), die auf dem Stack oder im Speicher des Programms vorhanden sind
        \item Diese \fatsf{Gadgets} enthalten Rückkehrbefehle (z.B. RET-Befehle), die vom Angreifer genutzt werden, um den Programmfluss umzuleiten un die Kontrolle zu übernehmen
        \item Anstatt neuen Schadcode auszuführen, kombiniert der Angreifer einfach vorhandene Codefragmente in einer \fatsf{bestimmten Reihenfolge}, um die gewünschte Funktion zu erreichen
    \end{enumerate}
\end{infoBox}
\subsubsection*{Gegenmaßnahmen: Randomiesierung}
\fatsf{ASLR:} Adress Space Layout Randomization
\begin{itemize}
    \item Angriffe benötigen Kenntnis an welcher Stelle im speicher Schadcode platziert wurde
    \item Idee: Randomisiere Adressbereich eines Programms\\
    $\rightarrow$ Angreifer kann RIP nicht mehr so leicht korrekt setzen
\end{itemize}
\fatsf{ASLR} umgehen:
\begin{itemize}
    \item Spraying: Verbreite den Schadecode großflächig im Speicher
    \item Raten der Adresse: nur möglich auf 32-Bit Systemen
\end{itemize}

\begin{itemize}

\subsubsection*{Flush + Reload: Überblick}
\begin{infoBox}
    Flush + Reload ist ein \fatsf{Cache Side-Channel Angriff}, der es einem Angreifer ermöglicht, geheime Daten aus dem Speicher eines anderen Prozesses zu lesen, indem er die \fatsf{Cache-Zugriffszeiten} misst\\
    \fatsf{Ziel:}\\
    Den Wert eines \fatsf{geheimen Bytes} (data) herausfinden, indem überprüft wird, welche Speicheradresse schneller zugreifbar ist (also im Cache liegt)
\end{infoBox}
\fatsf{Ziel:} Lese ein Byte \blue{data} aus dem Speicher
\begin{enumerate}
    \item Allokiere Speicher für ein \red{probe\_array}, sorge dafür, dass keine Daten davon im Cache sind
    \item Lade einen Eintrag des Arrays in den Cache, dessen Adresse von \blue{data} abhängt
    \item Ermittle die im Cache vorhandene Adresse und berechne daraus \blue{data}
    \begin{itemize}
        \item \enquote{Kurzes} Timing = Adresse \fatsf{in} Cache vorhanden
        \item \enquote{Langes} Timing = Adresse \fatsf{nicht} im Cache
    \end{itemize}
\end{enumerate}

\subsubsection*{Out-Of-Order Ausführung}
\begin{infoBox}
    Out-of-Order Execution (OoOE) ist eine Technik, die moderne Prozessorenverwenden, um die Leistung zu verbessern. Dabei werden Befehle \fatsf{nicht in der Reihenfolge des Programmcodes ausgeführt}, sondern so umsortiert, dass der Prozessor effizient arbeiten kann
\end{infoBox}
\begin{itemize}
    \item Ausführung zunächst ohne Zugriffskontrolle
    \begin{itemize}
        \item Kontrolle erst zum Ende der Ausführungspipeline
    \end{itemize}
    \item Instruktion \enquote{irrtümlich} ausgeführt:
    \begin{itemize}
        \item Rollback von Registern
        \item \fatsf{KEIN Cache-Rollback}
    \end{itemize}
\end{itemize}
\begin{infoBox}[title=Wie funktioniert Out-of-Order Execution?]
    \begin{enumerate}
        \item Der Prozessor analysiert die Befehle und sucht unabhängige Instruktionen
        \begin{itemize}
            \item Falls eine Instruktion auf das Ergebnis einer vorherigen wartet, kann eine spätere Instruktion bereits ausgeführt werden
        \end{itemize}
        \item Die Instruktionen werden \enquote{irrtümlich} ausgeführt, bevor alle Bedingungen geprüft werden
        \begin{itemize}
            \item Das bedeutet: Ein Zugriff auf geschützte Daten kann bereits stattfinden, bevor die CPU feststellt, dass der Zugriff nicht erlaubt ist
        \end{itemize}
        \item Am Ende der Pipeline wird geprüft, ob der Befehl erlaubt war
        \begin{itemize}
            \item Falls nicht, macht der Prozessor ein \fatsf{Rollback der Register} (die CPU \enquote{vergisst} die falsch Berechnung)
            \item \fatsf{Aber:} Der Cache bleibt unverändert - und genau hier liegt das Problem!
        \end{itemize}
    \end{enumerate}
\end{infoBox}

\subsubsection*{Branch vorhersage}
\begin{figure}[h]
    \centering
    \includegraphics[width=1\textwidth]{Thema_8_Images/Branch vorhersage.jpeg}
\end{figure}
\begin{itemize}
    \item In den allermeisten Fällen wird \red{pos} innerhalb des Arrays liegen
    \item Moderne Prozessoren starten die Ausführung der nächsten Transaktion bevor die vorherige beendet ist \fatsf{(Pipelining)}
    \item \fatsf{Branch Prediction Unit} in der CPU entscheidet welche Verzweigung wahrscheinlicher ist. Diese wird \fatsf{spekulativ ausgeführt}
    \item Falsche Vorhersage führt zu Rollback, aber \fatsf{kein Cache Rollback}
    \item \fatsf{Branch Prediction Unit} \enquote{lernt} dynamisch um Vorhersage zu verbessern
\end{itemize}
\begin{infoBox}[title=Wie funktioniert Branch Prediction?]
    \begin{enumerate}
        \item Verzweigungen im Code (if/else, loops) verursachen Pipeline-Stalls:
        \begin{itemize}
            \item Beispiel:
            \begin{codeBlock}{}
                if (0 <= pos && pos < array_len){
                    res = array[pos];
                }
            \end{codeBlock}
            \item Die CPU \fatsf{weiß nicht sofort}, ob pos im gültigen Bereich ist, weil sie erst den Wert aus dem Speicher holen muss
        \end{itemize}
        \item Die CPU rät (spekulative Ausführung):
        \begin{itemize}
            \item Die \fatsf{Branch Prediction Unit} (BPU) sagt voraus, dass der häufigere Fall (pos < array\_len) eintreten wird
            \item Falls die Vorhersage falsch ist, wird ein \fatsf{Rollback durchgeführt}
            \item \fatsf{Problem:} Der Cache wird nicht zurückgesetzt, was zu Seitenkanal-Angriffen führen kann!
        \end{itemize}
    \end{enumerate}
\end{infoBox}
\begin{infoBox}[title=Missbrauch der Branch Prediction für Angriffe (Spectre)]
    Angreifer können die \fatsf{CPU trainieren}, um falsche Speicherzugriffe spekulativ auszuführen:\\
    \fatsf{Angriffsidee:}
    \begin{enumerate}
        \item Der Angreifer trainiert die CPU auf eine häufige Bedingung:
        \begin{itemize}
            \item Führt mehrmals \fatsf{valide} Zugriffe (pos < array\_len) aus, damit die CPU glaubt, dass das immer der Fall ist
        \end{itemize}
        \item Dann gibt er eine spezielle Eingabe, die außerhalb des erlaubten Bereichs liegt:
        \begin{itemize}
            \item pos = sehr große Zahl, sodass array1[pos] auf eine geschützte Kernel-Adresse zeigt
        \end{itemize}
        \item Die CPU glaubt, dass der Zugriff erlaubt ist und führt spekulativ aus:
        \begin{codeBlock}{}
            temp = probe_array[array1[x] * 4096];
        \end{codeBlock}
        \begin{itemize}
            \item Der Wert aus dem geschützten Speicher beeinflusst den Cache!
        \end{itemize}
        \item Der Angreifer misst den Cache und kann den geheimen Wert rekonstruieren!
    \end{enumerate}
\end{infoBox}

\subsubsection*{Gegenmaßnahmen}
\begin{itemize}
    \item Einschränkung der spekulativen Ausführung
    \item Performanzeinbußen, Neu-Kompilierung von Anwendungen
    \item OpenBSD: Hyperthreading deaktiviert im Juni 2018 als Gegenmaßnahme für Spectre
\end{itemize}
$\Rightarrow$ Grundsätzliches Hardware/OS Re-Design

\subsubsection*{Lessons Learned}
\begin{itemize}
    \item Nur privilegierter Speicer im User-Adressraum $\rightarrow$ \blue{Sicher}
    \item Nur Out-of-Order und spekulative Ausfürhung $\rightarrow$ \blue{Sicher}
    \item Nur Caching $\rightarrow$ \blue{Sicher}
    \item Kombination $\rightarrow$ \red{Unsicher}
\end{itemize}
\begin{itemize}
    \item IT-Sicherheit muss das \enquote{Big Picture} im Blick haben
    \item Wir benötigen \fatsf{noch bessere Methodik}, um Security by Design zu erreichen!
\end{itemize}
